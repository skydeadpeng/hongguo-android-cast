# Android 公告请求阻塞播放入口

2026-11-11，基线 `805f747`。

## 复现与边界

在 API 30 x86_64 软件模拟器上，独立 QA 包正常加载首页后，`getInfo` 和 `play` 请求均超过 15 秒没有回执，也未进入播放器。只读 Java 线程栈显示两条通用工作线程都停在：

`Linux.android_getaddrinfo → HttpsURLConnection.getResponseCode → AnnouncementClient.read → AnnouncementClient.fetch → NativeBridge.handle`

主线程和 JavaScript 桥线程没有被挂起。正常/紧急公告在启动时分别发起请求，每次原生请求都会读取两个频道，两次请求足以占满通用池的两条线程。`play`、`getInfo` 与它们共用该池，因此排队等待。`HttpURLConnection` 的连接与读取超时并不能保证中断系统 DNS。

这是可由慢或不返回的 DNS 触发的工作线程隔离缺陷。模拟器云网络触发了它，但尚未取得用户实体设备的同类调用栈，不能认定这就是其全部视频不能播放的唯一原因。签名偏移防护和此缺陷是两件独立的问题。

## 修复

- 公告在进入通用工作池前分流到全进程共享的单线程通道，不占用播放、控制、搜索或账号线程。
- 网络通道不排队、不在页面重载时重建。系统 DNS 即使忽略中断，仍最多占用一条公告线程；后续请求直接返回暂不可用，不创建替代线程。
- 同时的普通、紧急和手动查询共用一次读取，最多保存 16 个等待回执；12 秒截止后返回暂不可用并清理回调。中断只作为尽力取消，不宣称能终止系统 DNS。
- 迟到的读取结果不能再次回执。截止后的读取不会继续尝试其他镜像或频道。页面关闭及 UI 排队期间原有的桥生命周期校验保持不变。
- 原来的公告地址、镜像顺序、TLS、重定向策略、字节上限、设置、已读与免提醒记录均未改变。
